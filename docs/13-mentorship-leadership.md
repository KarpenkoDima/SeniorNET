## 1. Роль Senior-разработчика в команде

### Что отличает Senior от Middle

| Аспект | Middle | Senior |
|---|---|---|
| **Задачи** | Выполняет задачи, заданные другими | Сам определяет задачи и декомпозирует их |
| **Скоуп** | Фича или модуль | Система или подсистема целиком |
| **Самостоятельность** | Нуждается в направлении | Работает автономно, сам определяет приоритеты |
| **Влияние** | На свой код | На архитектуру, процессы, команду |
| **Коммуникация** | С ближайшими коллегами | С другими командами, менеджментом, стейкхолдерами |
| **Отношение к проблемам** | Решает поставленную проблему | Находит проблемы и предлагает решения |
| **Менторство** | Учится сам | Учит других, поднимает уровень команды |

### Три главных обязанности Senior-разработчика

1. **Delivery** — доставлять результат: не просто писать код, а решать бизнес-проблемы
2. **Multiply** — мультиплицировать: делать команду сильнее, чтобы 5 разработчиков работали как 7
3. **Guide** — направлять: принимать технические решения, задавать стандарты, защищать качество

> **Ключевой инсайт:** Senior, который пишет идеальный код, но не поднимает уровень команды — это просто дорогой Middle. Настоящий Senior делает всю команду лучше.

## 2. Менторство: как учить и развивать других

### Формы менторства

| Формат | Описание | Когда использовать |
|---|---|---|
| **Pair Programming** | Совместная работа над кодом в реальном времени | Сложная задача, онбординг |
| **Code Review** | Асинхронная проверка кода с обучающей обратной связью | Повседневная работа |
| **1-on-1** | Регулярные личные встречи | Карьерное развитие, проблемы |
| **Tech Talks** | Презентации для команды | Новые технологии, паттерны |
| **Mob Programming** | Вся команда работает над одной задачей | Архитектурные решения, сложные баги |
| **Документация** | Гайды, ADR, runbooks | Масштабирование знаний |

### Принципы эффективного менторства

**1. Не давайте рыбу — учите ловить:**

```
❌ «Здесь нужно использовать ConcurrentDictionary вместо Dictionary.»

✅ «Эта коллекция используется из нескольких потоков.
    Что может произойти при параллельном доступе к Dictionary?
    Какие потокобезопасные альтернативы ты знаешь?
    Давай посмотрим, что подходит лучше для нашего случая.»
```

**2. Задавайте вопросы вместо приказов:**

```
❌ «Перепиши это с использованием паттерна Strategy.»

✅ «У нас уже три if-else ветки для разных типов оплаты,
    и скоро добавится четвёртая. Как думаешь,
    есть ли способ сделать это более расширяемым?»
```

**3. Давайте контекст, а не просто ответы:**

```
❌ «Используй async/await здесь.»

✅ «Этот endpoint обрабатывает 200 запросов в секунду.
    Сейчас синхронный вызов к БД блокирует поток из thread pool.
    При 200 RPS мы можем исчерпать пул. Как async/await
    поможет использовать потоки эффективнее?»
```

**4. Создавайте безопасную среду для ошибок:**

```
❌ «Это неправильно. Кто так делает?»

✅ «Интересный подход. Я вижу потенциальную проблему
    с производительностью при большой нагрузке —
    давай вместе разберём, почему.»
```

### Как подтягивать Junior-разработчиков

1. **Первые 2 недели:** Pair programming на реальных задачах. Не бросайте на CRUD — дайте понять архитектуру.
2. **1-3 месяца:** Самостоятельные задачи с подробным code review. Задачи увеличивающейся сложности.
3. **3-6 месяцев:** Ответственность за фичу. Вы — safety net, а не микроменеджер.
4. **6+ месяцев:** Они начинают ревьюить код других. Вы помогаете с архитектурными решениями.

## 3. Code Review как инструмент роста

### Философия Code Review

Code review — это не про «поиск багов». Это про:
- **Обучение** — распространение знаний в команде
- **Качество** — поддержание стандартов кодовой базы
- **Коммуникация** — совместное владение кодом (collective code ownership)

### Что смотреть на Code Review

| Приоритет | Что проверять | Примеры |
|---|---|---|
| **Критический** | Корректность, безопасность | SQL Injection, race conditions, потеря данных |
| **Высокий** | Архитектура, дизайн | Нарушение SOLID, leaky abstractions, coupling |
| **Средний** | Производительность | N+1, лишние аллокации, отсутствие кэширования |
| **Низкий** | Стиль, нейминг | Несоответствие конвенциям, нечитабельный код |

### Как давать обратную связь

**Уровни комментариев:**
- `[blocker]` — Нужно исправить до merge. Баг, уязвимость, архитектурная проблема.
- `[suggestion]` — Рекомендация. Можно обсудить, не обязательно к исполнению.
- `[question]` — Вопрос. Хочу понять логику, может быть я чего-то не вижу.
- `[nit]` — Мелочь. Стиль, форматирование. Не блокирует merge.
- `[praise]` — Похвала. Отличное решение, красивый код.

**Примеры хороших комментариев:**

```
[blocker] Здесь нет проверки на null перед вызовом .Value.
Если user не найден, получим NullReferenceException в production.
Предлагаю: if (user is null) return NotFound();

[suggestion] Этот LINQ-запрос делает SELECT * из таблицы с 2M записей,
а потом фильтрует в памяти. Предлагаю перенести Where до ToListAsync():
  var orders = await _context.Orders
      .Where(o => o.Status == status)
      .Select(o => new OrderDto { ... })
      .ToListAsync();

[question] Почему здесь catch всех исключений?
Нет ли риска, что мы проглотим важную ошибку
(например, SqlException при потере соединения с БД)?

[praise] Отличное использование Channel<T> здесь —
намного элегантнее, чем было с BlockingCollection.
Backpressure из коробки!
```

### Code Review Anti-patterns

| Антипаттерн | Проблема | Решение |
|---|---|---|
| «Я бы сделал иначе» | Навязывание стиля без объективных причин | Аргументируйте через принципы, а не вкусы |
| Мега-PR на 3000 строк | Невозможно нормально отревьюить | Договоритесь о максимуме (300-500 строк) |
| Ревью через 3 дня | Блокирует коллег | SLA на review: < 4 часов |
| Только негатив | Демотивирует команду | Отмечайте хорошие решения |
| «LGTM» без просмотра | Нет пользы от ревью | Оставляйте хотя бы 1 содержательный комментарий |
| Bikeshedding | Споры о мелочах | Автоматизируйте стиль (EditorConfig, analyzers) |

### Автоматизируйте то, что можно автоматизировать

```xml
<!-- .editorconfig + Roslyn Analyzers вместо ручных замечаний по стилю -->
<!-- Directory.Build.props -->
<Project>
  <PropertyGroup>
    <TreatWarningsAsErrors>true</TreatWarningsAsErrors>
    <EnforceCodeStyleInBuild>true</EnforceCodeStyleInBuild>
    <AnalysisLevel>latest-recommended</AnalysisLevel>
  </PropertyGroup>
</Project>
```

## 4. Техническое лидерство без формальной власти

### Модель технического лидерства

```
                    ┌─────────────────┐
                    │   Tech Vision   │  ← Куда мы идём
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
     ┌────────▼───────┐ ┌───▼────────┐ ┌──▼──────────┐
     │   Standards    │ │  Decisions │ │   Culture    │
     │ Coding style   │ │ ADR        │ │ Обучение     │
     │ Архитектура    │ │ Trade-offs │ │ Code review  │
     │ Тестирование   │ │ PoC        │ │ Психологич.  │
     │ CI/CD          │ │ RFC        │ │ безопасность │
     └────────────────┘ └────────────┘ └─────────────┘
```

### Как вести за собой без должности «Lead»

1. **Берите ответственность** — Не ждите, пока назначат. Видите проблему — предлагайте решение и берите на себя.
2. **Будьте предсказуемым** — Последовательность в принципах. Команда должна знать, за что вы стоите.
3. **Слушайте** — 70% слушать, 30% говорить. Лучшие решения часто приходят от тех, кого мало слышно.
4. **Признавайте ошибки** — «Моё решение использовать MongoDB для этого было неудачным, и вот почему...» — это усиливает авторитет.
5. **Делегируйте и доверяйте** — Не нужно всё делать самому. Давайте другим возможность расти.

### Зоны влияния Senior-разработчика

| Зона | Примеры |
|---|---|
| **Код** | Архитектурные решения, паттерны, стандарты кодирования |
| **Процессы** | CI/CD, code review, branching strategy, Definition of Done |
| **Люди** | Менторство, найм (участие в собеседованиях), onboarding |
| **Продукт** | Технические ограничения и возможности, помощь в приоритизации |
| **Организация** | Tech talks, внутренние инструменты, cross-team инициативы |

## 5. Принятие технических решений

### Фреймворк для принятия решений

```
1. Определите проблему     → Что именно мы решаем?
2. Соберите контекст       → Ограничения, требования, стейкхолдеры
3. Предложите варианты     → Минимум 2-3 альтернативы
4. Оцените trade-offs     → Плюсы/минусы каждого варианта
5. Примите решение         → Зафиксируйте «почему»
6. Коммуницируйте          → Расскажите команде
7. Ревьюите                → Вернитесь через время и оцените результат
```

### Пример: выбор брокера сообщений

```
Проблема: Нужна асинхронная коммуникация между OrderService и PaymentService.

Контекст:
- 500 заказов/минуту (пиково 2000)
- Порядок обработки важен
- Команда знакома с RabbitMQ
- Бюджет на инфраструктуру ограничен

Варианты:
┌─────────────┬───────────────────────┬──────────────────────┐
│             │ RabbitMQ              │ Kafka                │
├─────────────┼───────────────────────┼──────────────────────┤
│ Throughput  │ Достаточно для наших  │ Избыточно            │
│             │ 2000 msg/min          │                      │
├─────────────┼───────────────────────┼──────────────────────┤
│ Ordering    │ Да, в рамках очереди  │ Да, в рамках партиции│
├─────────────┼───────────────────────┼──────────────────────┤
│ Знание      │ Команда знает         │ Нужно учиться        │
│ команды     │                       │                      │
├─────────────┼───────────────────────┼──────────────────────┤
│ Ops         │ Простое               │ Сложное (ZooKeeper)  │
│ сложность   │                       │                      │
├─────────────┼───────────────────────┼──────────────────────┤
│ Стоимость   │ Меньше ресурсов       │ Больше ресурсов      │
└─────────────┴───────────────────────┴──────────────────────┘

Решение: RabbitMQ
Почему: Достаточная пропускная способность, команда уже имеет опыт,
проще в эксплуатации. Kafka избыточна для наших объёмов.
Переход на Kafka рассмотрим при росте до 50K msg/min.
```

### Когда НЕ принимать решение

- **Когда не хватает информации** — лучше подождать, чем угадывать
- **Когда решение обратимо** — не тратьте время на долгий анализ, попробуйте и откатите
- **Когда это не ваше решение** — не перетягивайте одеяло, уважайте зоны ответственности

> **Правило:** Необратимые решения (выбор БД, языка, архитектуры) — анализируйте тщательно. Обратимые (библиотека, паттерн, формат API) — принимайте быстро, корректируйте по ходу.

## 6. ADR: Architecture Decision Records

### Что такое ADR

ADR — документ, фиксирующий архитектурное решение: что решили, почему, какие альтернативы рассматривали.

### Шаблон ADR

```markdown
# ADR-001: Использование PostgreSQL вместо SQL Server

## Статус
Принято (2024-03-15)

## Контекст
Мы запускаем новый микросервис для управления каталогом.
Текущая инфраструктура на Azure, но рассматриваем мультиклауд.
SQL Server требует дорогую лицензию для production.

## Решение
Используем PostgreSQL 16 через Azure Database for PostgreSQL Flexible Server.

## Последствия
### Позитивные
- Экономия ~$500/мес на лицензиях
- Мультиклауд совместимость
- Лучшая поддержка JSON-операций для нашей доменной модели
- Active open-source community

### Негативные
- Команде нужно изучить отличия от SQL Server
- Некоторые ORM-фичи EF Core работают иначе
- Нет SQL Server Agent для фоновых задач

### Риски
- Миграция существующих сервисов потребует усилий
- Нужно обновить CI/CD pipeline

## Рассмотренные альтернативы
1. **SQL Server** — дорого, vendor lock-in
2. **MySQL** — менее зрелая поддержка в EF Core
3. **CockroachDB** — избыточно для наших масштабов
```

### Где хранить ADR

```
docs/
├── adr/
│   ├── 001-use-postgresql.md
│   ├── 002-adopt-cqrs-pattern.md
│   ├── 003-switch-to-kubernetes.md
│   └── template.md
```

ADR хранятся в репозитории вместе с кодом — они проходят code review и версионируются.

## 7. Работа с техническим долгом

### Классификация технического долга

| Тип | Описание | Пример |
|---|---|---|
| **Намеренный** | Осознанный компромисс ради скорости | «Сделаем без кэша, добавим позже» |
| **Ненамеренный** | Появился из-за недостатка знаний | Не знали про race condition |
| **Bit rot** | Код устарел со временем | Deprecated API, старые зависимости |
| **Архитектурный** | Неверные фундаментальные решения | Монолит, который нужен микросервисом |

### Квадрант технического долга (Martin Fowler)

```
              Намеренный              Ненамеренный
         ┌────────────────────┬────────────────────┐
Благо-   │ "Сейчас шипнем,   │ "Не знали лучшего  │
разумный │  потом рефакторим" │  способа; теперь    │
         │                    │  знаем"             │
         ├────────────────────┼────────────────────┤
Безрас-  │ "Нет времени на   │ "Что такое          │
судный   │  дизайн"           │  Layered Arch?"     │
         └────────────────────┴────────────────────┘
```

### Как продать рефакторинг менеджменту

Менеджеры не понимают «технический долг». Говорите на языке бизнеса:

```
❌ «Нам нужно отрефакторить модуль заказов, там плохой код.»

✅ «Сейчас добавление нового типа оплаты занимает 3 недели
    из-за сцепленности модуля заказов. После рефакторинга — 3 дня.
    Через квартал нам нужно добавить 4 новых метода оплаты.
    Инвестиция: 2 спринта. Экономия: 9 недель за квартал.»
```

### Стратегии управления техдолгом

1. **Boy Scout Rule** — оставляй код чище, чем нашёл. Мелкие улучшения в каждом PR.
2. **Tech Debt Sprint** — каждый N-й спринт посвящён исключительно техдолгу.
3. **20% Rule** — 20% capacity каждого спринта на техдолг.
4. **Strangler Fig** — постепенная замена legacy новым кодом.
5. **Tech Debt Backlog** — ведите отдельный бэклог техдолга с приоритетами.

## 8. Оценка задач и планирование

### Почему оценки врут

- **Оптимизм** — мы оцениваем happy path
- **Неизвестные неизвестные** — то, чего мы не знаем, что мы не знаем
- **Закон Хофштадтера** — «Всё всегда занимает больше времени, чем ожидаешь, даже если учесть закон Хофштадтера»
- **Якорение** — первая оценка влияет на все последующие

### Техники оценки

**1. Planning Poker:**
- Каждый оценивает независимо
- Обсуждаем крайние оценки
- Переоцениваем до консенсуса

**2. T-Shirt Sizing:**
- S, M, L, XL — грубая оценка
- Быстро, хорошо для roadmap

**3. Трёхточечная оценка:**
```
Оптимистичная (O) = 2 дня
Реалистичная  (M) = 5 дней
Пессимистичная(P) = 12 дней

Ожидаемая = (O + 4M + P) / 6 = (2 + 20 + 12) / 6 = 5.7 дней
```

### Декомпозиция задач

```
Плохо: «Реализовать модуль оплаты» → ???

Хорошо:
├── Создать модель PaymentOrder (0.5 дня)
├── Реализовать интеграцию с Stripe API (2 дня)
│   ├── Payment Intent creation
│   ├── Webhook handler
│   └── Refund flow
├── Написать unit-тесты (1 день)
├── Написать integration-тесты со Stripe sandbox (1 день)
├── Code review + исправления (0.5 дня)
└── Тестирование на staging (0.5 дня)
    Итого: ~5.5 дней + буфер 20% = ~7 дней
```

> **Правило:** Если задача оценивается больше чем в 3 дня — она недостаточно декомпозирована.

## 9. Onboarding новых разработчиков

### Чеклист онбординга

**День 1:**
- [ ] Доступы: Git, CI/CD, облако, мониторинг, мессенджеры
- [ ] Настройка локального окружения (скрипт `setup.sh` / README)
- [ ] Обзор архитектуры: 30-минутная сессия с доской
- [ ] Первый PR: что-то маленькое (typo fix, мелкий баг)

**Неделя 1:**
- [ ] Pair programming на реальной задаче
- [ ] Обзор CI/CD pipeline
- [ ] Знакомство с мониторингом (Grafana, Kibana, Application Insights)

## 10. Работа с конфликтами в команде

### Типичные технические конфликты

| Конфликт | Пример | Как решать |
|---|---|---|
| **Архитектурный** | REST vs gRPC | PoC обоих вариантов, ADR с обоснованием |
| **Стиль кода** | Tabs vs Spaces | Автоматизируйте (EditorConfig), не спорьте |
| **Подход к задаче** | YAGNI vs Extensibility | Обсудите конкретные требования, а не философию |
| **Инструменты** | Docker vs Podman | Позвольте попробовать, выберите по результатам |
| **Технический долг** | Рефакторить vs Шипить | Количественно оцените стоимость долга |

### Техника разрешения конфликтов

**1. Переведите в объективную плоскость:**
```
❌ «Мне кажется, Repository Pattern здесь лишний.»
✅ «Давайте посмотрим: этот сервис имеет 2 метода и вряд ли
    вырастет. Стоит ли добавлять слой абстракции ради 2 методов?
    Можем ли мы добавить его позже, если понадобится?»
```

**2. Используйте данные:**
```
❌ «Dapper быстрее EF Core!»
✅ «Давайте сделаем бенчмарк на нашем реальном запросе.
    Если разница < 5мс, используем EF Core ради DX.
    Если > 50мс — Dapper для этого запроса.»
```

**3. Disagree and Commit:**
Если консенсус не достигнут — голосование или решение tech lead. Проигравшая сторона поддерживает решение.

## 11. Influence Without Authority

### Как убедить, не имея формальной власти

**1. Создайте PoC:**
Код убеждает лучше слов. Вместо часового спора — 2-часовой прототип.

**2. Покажите данные:**
```
«Наши тесты идут 45 минут. Вот graph: за полгода время
выросло с 15 до 45 мин. Если не оптимизируем, через 3 месяца
будет > 1 часа. Предлагаю: параллелизация + отказ от E2E
на каждый коммит.»
```

**3. Найдите союзников:**
Обсудите идею 1-on-1 с коллегами до общей встречи. К моменту обсуждения у вас уже есть поддержка.

**4. Начните с малого:**
Не предлагайте «переписать всё на микросервисы». Предложите «извлечь один сервис как пилот».

**5. Решайте проблему, а не продвигайте технологию:**
```
❌ «Давайте внедрим Kubernetes!»
✅ «У нас проблема: деплой занимает 40 минут и требует
    ручных шагов. Вот три варианта решения, один из которых
    включает K8s. Давайте оценим все три.»
```

## 12. Рост от Senior к Lead/Architect

### Карьерные треки

```
                    ┌──────────────┐
                    │   Senior     │
                    │   Developer  │
                    └──────┬───────┘
                           │
              ┌────────────┼────────────┐
              │                         │
     ┌────────▼───────┐       ┌────────▼───────┐
     │   Tech Lead    │       │   Staff        │
     │                │       │   Engineer     │
     └────────┬───────┘       └────────┬───────┘
              │                         │
     ┌────────▼───────┐       ┌────────▼───────┐
     │   Engineering  │       │   Principal    │
     │   Manager      │       │   Engineer /   │
     │                │       │   Architect    │
     └────────────────┘       └────────────────┘

     Management Track          Individual Contributor Track
```

### Что нужно для роста

| Уровень | Скоуп | Ключевые навыки |
|---|---|---|
| **Senior** | Команда, подсистема | Глубокая экспертиза, менторство, самостоятельность |
| **Staff** | Несколько команд | Cross-team инициативы, техническая стратегия |
| **Principal** | Организация | Влияние на уровне компании, industry thought leadership |

### Что делать для перехода на следующий уровень

1. **Расширяйте скоуп** — берите задачи, которые затрагивают несколько команд
2. **Думайте системно** — не «мой сервис», а «вся платформа»
3. **Коммуницируйте вверх** — менеджмент должен понимать техническую стратегию
4. **Создавайте leverage** — инструменты, гайдлайны, шаблоны, которые ускоряют всех
5. **Развивайте бизнес-мышление** — понимайте, как технические решения влияют на бизнес

## 13. Вопросы на собеседовании с ответами

### Q1: Расскажите о ситуации, когда вы менторили junior-разработчика. Что было сложнее всего?

**Пример ответа:**
«В моей команде был Junior, который писал рабочий, но "наивный" код — без учёта edge cases, производительности и тестируемости. Вместо того чтобы просто указывать на ошибки в PR, я начал с pair programming.

Мы вместе работали над задачей: он вёл, я комментировал. Я задавал вопросы: "А что будет, если тут придёт null?", "Как это будет работать при 10K записей?". Через месяц он сам начал задавать себе эти вопросы.

Сложнее всего было не делать за него. Иногда быстрее написать самому, но тогда он ничему не научится. Я установил правило: если задача некритична по срокам — Junior делает сам, я только ревьюю.

Через полгода он стал самостоятельно закрывать задачи уровня Middle. Это была лучшая инвестиция моего времени.»

### Q2: Как вы принимаете архитектурные решения в условиях неопределённости?

**Пример ответа:**
«Я использую подход "last responsible moment" — откладываю необратимые решения до момента, когда дальнейшее откладывание дороже ошибки.

Конкретный пример: при проектировании нового сервиса мы не знали, будет ли нагрузка 100 RPS или 10K RPS. Вместо выбора между PostgreSQL и Cassandra мы:

1. Использовали Repository Pattern для абстракции от хранилища
2. Начали с PostgreSQL (проще, команда знает)
3. Написали нагрузочные тесты
4. Через 2 месяца стало понятно — 500 RPS, PostgreSQL справляется

Если бы мы сразу выбрали Cassandra "на будущее", потратили бы лишний месяц на операционную сложность, которая не нужна.

Ключевой принцип: для необратимых решений — тщательный анализ. Для обратимых — быстрое решение и корректировка.»

### Q3: Вы не согласны с техническим решением lead/архитектора. Что будете делать?

**Пример ответа:**
«Сначала убеждаюсь, что я правильно понимаю контекст решения — возможно, у lead есть информация, которой нет у меня. Задаю вопросы: "Почему мы выбрали X, а не Y?"

Если после этого всё ещё не согласен — готовлю аргументацию:
1. В чём конкретно проблема предложенного решения
2. Альтернативный вариант с trade-offs
3. По возможности — PoC или бенчмарк

Представляю это на обсуждении команды, а не в личной переписке — чтобы решение было коллективным.

Если команда всё равно выбирает решение, с которым я не согласен — я принимаю его и реализую качественно. "Disagree and commit". Саботировать или говорить "я же предупреждал" — это токсично и непродуктивно.»

### Q4: Как вы обрабатываете ситуацию, когда бизнес давит на сроки, а вы видите, что нужен рефакторинг?

**Пример ответа:**
«Я перевожу технический долг на язык бизнеса. Не "нам нужен рефакторинг", а "текущая архитектура модуля X означает, что каждая новая фича занимает на 40% дольше".

Конкретно: делаю оценку двух вариантов:
- **Без рефакторинга:** фича A = 3 нед, фича B = 3 нед, фича C = 4 нед. Итого: 10 недель.
- **С рефакторингом:** рефакторинг = 2 нед, фича A = 1 нед, фича B = 1 нед, фича C = 1.5 нед. Итого: 5.5 недель.

Бизнес видит: инвестиция 2 недели экономит 4.5 недели. Это не "техдолг" — это ROI.

Если бизнес всё равно говорит "нет" — окей, фиксирую решение в ADR, добавляю в техдолг-бэклог, и мы знаем, что вернёмся к этому позже.»

### Q5: Как вы поддерживаете качество кода в команде из 8 разработчиков?

**Пример ответа:**
«Комбинация автоматизации и культуры:

**Автоматизация:**
- EditorConfig + Roslyn Analyzers — единый стиль, нет споров
- Обязательный code review (минимум 1 approve)
- CI с тестами, линтерами и проверкой покрытия (не ниже 80%)
- SonarQube на критические уязвимости

**Культура:**
- Я провожу "архитектурные сессии" раз в 2 недели — разбираем реальные решения из наших PR
- Code review guidelines — задокументированы, новички получают при онбординге
- Я сам прошу ревьюить мой код и показываю, что замечания — это нормально
- Celebrate good code — отмечаю элегантные решения коллег в общем чате

Результат: за полгода количество production-багов снизилось на 35%.»

### Q6: Как вы боретесь с выгоранием (своим или в команде)?

**Пример ответа:**
«Для себя: отслеживаю сигналы — если начинаю откладывать PR или раздражаться на код, это звоночек. Помогает переключение: технический spike на новой технологии, выступление на внутреннем митапе, менторство — то, что даёт энергию.

Для команды: обращаю внимание на изменения — когда обычно активный человек замолкает, когда PR становятся формальными. Говорю 1-on-1: "Я заметил, что последние недели ты выглядишь уставшим. Как ты?"

Системно: слежу, чтобы не было перегрузки (WIP limits на доске), чтобы был баланс скучных и интересных задач, чтобы oncall не ложился на одних и тех же людей.»

> **Совет на собеседовании:** На поведенческих вопросах используйте формат STAR (Situation, Task, Action, Result). Конкретные примеры из опыта ценятся в 10 раз выше, чем теоретические рассуждения. Если точного примера нет — скажите честно и опишите, как бы вы действовали.
