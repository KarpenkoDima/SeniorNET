## 1. Почему Soft Skills критичны для Senior

### Пирамида навыков Senior-разработчика

```
              ▲
             /│\
            / │ \        Влияние на бизнес
           /  │  \       Стратегическое мышление
          /───┼───\
         /    │    \     Лидерство, менторство
        /     │     \    Коммуникация
       /──────┼──────\
      /       │       \  Архитектура, System Design
     /        │        \ Паттерны проектирования
    /─────────┼─────────\
   /          │          \ Алгоритмы, структуры данных
  /           │           \ Язык, фреймворки, инструменты
 /────────────┼────────────\
              Hard Skills
```

Чем выше уровень — тем больше soft skills. На позиции Senior минимум 40% работы — это коммуникация, а не код.

### Почему отличные программисты проваливают собеседования на Senior

| Причина провала | Пример |
|---|---|
| Не могут объяснить решение | Написал идеальную архитектуру, но не смог аргументировать выбор |
| Не слышат вопрос | Отвечают про паттерны, когда спрашивают про бизнес-проблему |
| Не задают вопросы | Начинают проектировать, не уточнив требования |
| Высокомерие | «Очевидно, что нужно использовать CQRS» без объяснения почему |
| Не признают ограничений | «Я всё знаю» вместо «В этой области мне нужно углубиться» |

> **Ключевое правило:** На Senior-собеседовании оценивают не только ЧТО вы знаете, но и КАК вы думаете, коммуницируете и принимаете решения.

## 2. Коммуникация с разными стейкхолдерами

### Адаптация языка под аудиторию

| Аудитория | Язык | Фокус | Пример |
|---|---|---|---|
| **Разработчики** | Технический | Как реализовать | «Используем Polly с Circuit Breaker и retry policy» |
| **Tech Lead / Архитектор** | Технический + trade-offs | Почему так, а не иначе | «Circuit Breaker предотвратит каскадный сбой; trade-off — дополнительная latency в 50ms» |
| **Product Owner** | Бизнес + сроки | Что получит пользователь | «Система будет автоматически переключаться на резервный сервис при сбое — пользователи не заметят проблему» |
| **Менеджмент** | Бизнес + ROI | Сколько стоит / экономит | «Внедрение займёт 1 неделю, но предотвратит даунтаймы, которые стоят $5K/час» |
| **Клиент / End User** | Простой | Какая польза | «Приложение будет работать стабильнее, даже если часть серверов недоступна» |

### Шаблон коммуникации для разных ситуаций

**Предложение технического решения:**
```
1. Проблема: [Что сейчас не так — 1 предложение]
2. Влияние: [Как это бьёт по бизнесу — числа]
3. Решение: [Что предлагаю — 2-3 предложения]
4. Стоимость: [Сколько времени/ресурсов нужно]
5. Альтернативы: [Что ещё рассматривал и почему отверг]
```

**Отчёт о проблеме (инцидент):**
```
1. Что произошло: [Факт, без эмоций]
2. Влияние: [Кто затронут, масштаб]
3. Статус: [Что сделано / делается]
4. Следующие шаги: [Что планируем]
5. ETA: [Когда ожидаем восстановление]
```

**Запрос на дополнительное время:**
```
1. Текущий статус: [Что сделано]
2. Что обнаружили: [Неожиданная сложность]
3. Варианты:
   a) Сделать быстро с ограничениями → [срок]
   b) Сделать полноценно → [срок]
4. Рекомендация: [Ваш выбор и почему]
```

## 3. Объяснение технических решений нетехническим людям

### Техники объяснения

**1. Аналогии из реального мира:**

```
Технический: «Мы реализовали caching layer с TTL 5 минут
для уменьшения нагрузки на БД.»

Для бизнеса: «Представьте библиотеку. Вместо того чтобы каждый
раз бежать в архив за книгой, библиотекарь кладёт популярные
книги на стойку у входа. Мы сделали то же самое — часто
запрашиваемые данные хранятся "ближе", и система отвечает
быстрее.»
```

```
Технический: «Нам нужно внедрить Circuit Breaker Pattern.»

Для бизнеса: «Как автомат-предохранитель в электрощитке.
Если один провод замкнул, предохранитель отключает именно
его, а не весь дом. Наш "предохранитель" изолирует
сломавшийся сервис, чтобы остальные продолжали работать.»
```

**2. Визуализация:**

Для сложных архитектурных решений рисуйте простые диаграммы. Не UML — простые квадраты и стрелки, которые поймёт PM.

**3. Правило "So What?":**

После каждого технического утверждения задайте себе «И что?» — пока не дойдёте до бизнес-ценности:

```
«Мы перешли на async/await.»
→ И что?
«Сервер обрабатывает больше запросов одновременно.»
→ И что?
«Мы можем обслужить в 3 раза больше пользователей
на тех же серверах.»
→ И что?
«Экономим $2000/мес на серверах при текущей нагрузке,
и не нужно масштабировать при росте до 3x.»
✅ — Вот это понятно бизнесу.
```

## 4. Проведение технических собеседований

### Роль Senior в процессе найма

Senior-разработчик участвует в собеседованиях не как «задающий каверзные вопросы», а как тот, кто оценивает, сможет ли кандидат эффективно работать в команде.

### Что оценивать

| Навык | Как проверить | Красные флаги |
|---|---|---|
| **Мышление** | Открытая задача на дизайн | Запрыгивает в код без анализа |
| **Коммуникация** | Просите объяснить решение | Не может объяснить свой же код |
| **Обучаемость** | Дайте подсказку и смотрите реакцию | Игнорирует подсказки |
| **Культура** | Ситуационные вопросы | «Я всегда прав», blame culture |
| **Глубина знаний** | Follow-up вопросы: «А почему?» | Знает «что», но не «почему» |
| **Опыт** | «Расскажите о проблеме, которую решали» | Только теория, нет реального опыта |

### Структура хорошего технического интервью

```
5 мин  — Знакомство, создание комфорта
10 мин — Обсуждение опыта (по резюме)
25 мин — Техническая задача / System Design
10 мин — Ситуационные/поведенческие вопросы
5 мин  — Вопросы кандидата
5 мин  — Завершение, следующие шаги
```

### Принципы хорошего интервьюера

1. **Создайте комфортную атмосферу** — стресс-интервью показывает стрессоустойчивость, а не компетенцию
2. **Давайте подсказки** — интервью это сотрудничество, а не экзамен
3. **Оценивайте процесс мышления** — правильный ответ без рассуждений стоит меньше, чем неправильный ответ с отличным ходом мысли
4. **Не задавайте гуглимые вопросы** — «Какие модификаторы доступа в C#?» не покажет уровень Senior
5. **Записывайте обратную связь сразу** — через 3 часа вы забудете нюансы

## 5. Презентация и публичные выступления

### Зачем Senior-разработчику уметь выступать

- **Внутренние tech talks** — делитесь знаниями, влияйте на техническую стратегию
- **RFC/Design Review** — защищайте архитектурные решения перед командой
- **Demo** — показывайте результаты стейкхолдерам
- **Конференции** — строите личный бренд и бренд компании
- **Собеседования** — уверенная речь = убедительный кандидат

### Структура технической презентации

```
1. Проблема          (1-2 мин) — Почему это важно? Боль аудитории.
2. Контекст          (2-3 мин) — Что мы знаем? Ограничения.
3. Решение           (5-10 мин) — Что мы предлагаем/сделали.
4. Демо / Код        (5-7 мин) — Покажите в действии.
5. Trade-offs        (2-3 мин) — Что мы потеряли, что получили.
6. Результат/Метрики (1-2 мин) — Числа.
7. Q&A               (5 мин)
```

### Советы по выступлению

- **Начните с "Зачем"** — не "Мы внедрили Redis", а "Наш API отвечал за 2 секунды"
- **Один слайд = одна идея** — не перегружайте информацией
- **Код на слайдах** — максимум 10-15 строк, подсветка ключевых частей
- **Практикуйтесь вслух** — хотя бы один прогон перед выступлением
- **Готовьте ответы на сложные вопросы** — подумайте, что спросят скептики

## 6. Навыки переговоров

### Переговоры в работе разработчика

| Ситуация | С кем | О чём |
|---|---|---|
| Оценка задачи | PM/PO | Сроки и скоуп |
| Технический долг | Менеджмент | Время на рефакторинг |
| Архитектурное решение | Другие разработчики | Выбор подхода |
| Salary negotiation | HR / Hiring Manager | Компенсация |
| Приоритеты | Стейкхолдеры | Что делаем первым |

### Принципы переговоров

**1. Знайте свою BATNA (Best Alternative To Negotiated Agreement):**
```
PM: «Нужно сделать за 2 недели.»
Вы: «За 2 недели можем сделать MVP без функции X.
     Полная версия — 4 недели. Что приоритетнее:
     скорость или полнота?»
```
Ваша BATNA — альтернативные варианты, которые вы предлагаете.

**2. Отделяйте людей от проблемы:**
```
❌ «Ты всегда ставишь нереальные дедлайны.»
✅ «Дедлайн в 2 недели не учитывает интеграционное
    тестирование. Давай посмотрим, что можно
    сделать за это время.»
```

**3. Фокусируйтесь на интересах, а не позициях:**
```
Позиция PM: «Нужно к пятнице.»
Интерес PM: «Клиент ждёт демо в понедельник.»

Решение: «К пятнице готовим демо-версию с основным
flow. Полная версия — через неделю.»
```

**4. Используйте объективные критерии:**
```
❌ «Мне кажется, это займёт дольше.»
✅ «Аналогичная задача в прошлом спринте заняла 8 дней.
    Эта сложнее из-за интеграции с внешним API.
    Реалистичная оценка: 10-12 дней.»
```

## 7. Управление временем и приоритизация

### Матрица Эйзенхауэра для разработчика

```
                    Срочно              Не срочно
              ┌─────────────────┬─────────────────┐
  Важно       │ ДЕЛАТЬ СЕЙЧАС   │ ПЛАНИРОВАТЬ     │
              │                 │                 │
              │ • Production    │ • Рефакторинг   │
              │   баг           │ • Изучение      │
              │ • Security      │   новых         │
              │   vulnerability │   технологий    │
              │ • Блокирующий   │ • Менторство    │
              │   PR review     │ • Документация  │
              │                 │ • Архитектурные │
              │                 │   улучшения     │
              ├─────────────────┼─────────────────┤
  Не важно    │ ДЕЛЕГИРОВАТЬ    │ ОТКАЗАТЬСЯ      │
              │                 │                 │
              │ • Рутинные      │ • Бесполезные   │
              │   митинги       │   митинги       │
              │ • Мелкие баги,  │ • Over-         │
              │   которые может │   engineering   │
              │   Junior        │ • Bikeshedding  │
              │ • Ops-задачи    │ • Споры о табах │
              │   для автомат-и │   vs пробелах   │
              └─────────────────┴─────────────────┘
```

### Техники управления временем

**1. Time Boxing:**
```
09:00-09:30 — Code review (не больше 30 мин)
09:30-12:00 — Deep work (код, никаких митингов)
12:00-13:00 — Обед
13:00-14:00 — Митинги, sync-ups
14:00-16:30 — Deep work
16:30-17:00 — PR review, менторство, Slack
```

**2. Правило двух минут:**
Если задача занимает менее 2 минут — делайте сразу, не записывайте в TODO.

**3. Батчинг:**
Группируйте однотипные задачи: все code review за один присест, все ответы в Slack за один раз.

### Борьба с отвлечениями

| Проблема | Решение |
|---|---|
| Slack-уведомления | Отключить на время deep work. Отвечать батчами. |
| «Можешь посмотреть?» | «Конечно, добавь в очередь — посмотрю в 16:30.» |
| Митинги без повестки | «Какая цель встречи? Могу ли я получить это из Slack?» |
| Context switching | WIP limit = 2 задачи максимум одновременно. |

## 8. Работа в распределённых командах

### Асинхронная коммуникация

В распределённых командах (разные тайм-зоны) асинхронность — ваш друг:

**Принципы:**
1. **Пишите, а не говорите** — подробный PR description лучше, чем «обсудим на митинге»
2. **Over-communicate** — лучше больше контекста, чем меньше
3. **Документируйте решения** — не в Slack, а в Wiki/ADR
4. **Записывайте митинги** — для тех, кто в другой тайм-зоне

### Хороший PR description

```markdown
## Что сделано
Добавлен rate limiting для API на основе sliding window.

## Зачем
Клиент X генерирует 10K запросов/мин, что влияет на latency
для остальных клиентов (p99 выросло с 200ms до 1.5s).

## Как
- Использован встроенный RateLimiter из .NET 7
- Sliding window: 1000 запросов/мин на клиента
- При превышении — 429 Too Many Requests
- Метрики в Prometheus (rate_limit_hits_total)

## Тестирование
- Unit-тесты: 12 новых
- Load test: 5000 RPS, p99 стабильно < 300ms
- Проверено на staging

## Скриншоты
[График latency до и после]

## Чеклист
- [x] Unit-тесты
- [x] Integration-тесты
- [x] Документация обновлена
- [x] Проверено на staging
```

### Культурные различия

| Аспект | Совет |
|---|---|
| Прямота | В некоторых культурах прямая критика — норма, в других — грубость. Будьте вежливы, но чётки. |
| Тайм-зоны | Уважайте рабочие часы коллег. Не ожидайте ответа в их ночь. |
| Языковой барьер | Пишите простым английским. Избегайте идиом и сленга. |
| Стиль общения | Кто-то предпочитает чат, кто-то — email. Адаптируйтесь. |

## 9. Обратная связь: давать и принимать

### Модель SBI (Situation-Behavior-Impact)

```
❌ «Ты пишешь плохой код.»

✅ Situation: «На прошлой неделе в PR для payment module...»
   Behavior:  «...ты не написал ни одного теста и не обработал
              ошибки от Stripe API...»
   Impact:    «...это привело к тому, что на staging мы получили
              необработанный 500 при невалидной карте. QA потратил
              2 часа на дебаг.»

   Следующий шаг: «Давай договоримся: каждый PR с бизнес-логикой
   включает минимум unit-тесты на happy path и основные ошибки.
   Могу помочь с первым разом.»
```

### Как давать обратную связь

1. **Своевременно** — не через месяц, а сразу (в течение 1-2 дней)
2. **Конкретно** — не «код плохой», а «вот этот метод на 150 строк сложно поддерживать»
3. **Приватно для негативной** — критика при всех = унижение
4. **Публично для позитивной** — похвала при всех = мотивация
5. **С фокусом на поведение, не личность** — не «ты невнимательный», а «в этом PR пропущена валидация»
6. **С предложением** — не только «что плохо», но и «как улучшить»

### Как принимать обратную связь

1. **Слушайте, не защищайтесь** — первая реакция «но...» — подавите её
2. **Уточняйте** — «Можешь привести конкретный пример?»
3. **Благодарите** — «Спасибо, что сказал. Я подумаю над этим.»
4. **Действуйте** — обратная связь без действий = потерянное время
5. **Не принимайте на свой счёт** — критика кода ≠ критика вас как личности

## 10. Управление стрессом и сложными ситуациями

### Типичные стрессовые ситуации

| Ситуация | Правильная реакция |
|---|---|
| **Production down** | Спокойно. Собрать факты. War room. Communicate статус. |
| **Нереальный дедлайн** | Не молчать. Эскалировать с данными. Предложить варианты. |
| **Токсичный коллега** | Документировать. Обратная связь 1-on-1. Если не помогает → менеджер. |
| **Burnout** | Признать. Поговорить с менеджером. Взять отпуск. |
| **Ошибка в production** | Не паниковать. Fix → Postmortem → Prevent. Blameless culture. |

### Incident Management — как вести себя при аварии

```
1. ДЫШИТЕ. Паника ухудшает решения.

2. ОЦЕНИТЕ масштаб:
   - Кто затронут? Все пользователи или сегмент?
   - Какой impact? Данные теряются или просто тормозит?

3. КОММУНИЦИРУЙТЕ:
   - Оповестите команду и стейкхолдеров
   - Создайте incident channel
   - Обновляйте статус каждые 15-30 минут

4. ИСПРАВЛЯЙТЕ:
   - Сначала mitigation (быстрый fix), потом root cause
   - Rollback если возможно
   - Один человек координирует, остальные исполняют

5. POSTMORTEM (blameless):
   - Что произошло (timeline)
   - Почему произошло (root cause)
   - Как предотвратить (action items)
```

### Blameless Postmortem

```
❌ «Вася задеплоил баг в production.»

✅ «Деплой содержал изменение, которое не было покрыто
    интеграционным тестом. Наш pipeline не проверяет
    сценарий X. Action item: добавить тест на сценарий X,
    добавить canary deployment.»
```

> Фокус на системе, а не на человеке. Если система позволяет одному человеку сломать production — это проблема системы.

## 11. Непрерывное обучение

### Стратегия обучения Senior-разработчика

**T-shaped expertise:**
```
Широкие знания (горизонталь)
──────────────────────────────────
DevOps │ Frontend │ Mobile │ ML │ ...
       │         │        │    │
       │         │        │    │
       │         │        │    │
       ▼ Глубокая│экспертиза    │
         (вертикаль)
       Backend .NET
       Distributed Systems
       System Design
```

### Источники обучения

| Тип | Примеры | Когда |
|---|---|---|
| **Книги** | Designing Data-Intensive Applications, CLR via C#, DDD (Evans), Clean Architecture | 30 мин/день |
| **Курсы** | Pluralsight, Udemy, Coursera | Для новых тем |
| **Блоги** | Стивен Клири, Владимир Хориков, Andrew Lock | Регулярно |
| **Конференции** | NDC, .NET Conf, DotNext | 2-3 в год |
| **Open Source** | Чтение исходников ASP.NET Core, EF Core | Для углубления |
| **Side Projects** | Свои проекты для экспериментов | Для практики новых технологий |
| **Peer Learning** | Tech talks в команде, book clubs | Еженедельно |

### Как эффективно учиться

1. **Учитесь "just in time", а не "just in case"** — не зубрите Kubernetes, если у вас нет задач с K8s. Но когда появится задача — погружайтесь глубоко.
2. **Учите через преподавание** — лучший способ понять тему — объяснить её другим (tech talk, статья, менторство).
3. **Строите, а не только читайте** — прочитали про Event Sourcing? Реализуйте простой прототип.
4. **Ведите "Learning Log"** — записывайте, что узнали нового. Через год удивитесь прогрессу.

## 12. Поведенческие вопросы на собеседовании (STAR)

### Метод STAR

- **S**ituation — Контекст: где, когда, что за проект
- **T**ask — Задача: что нужно было сделать
- **A**ction — Действия: что конкретно ВЫ сделали
- **R**esult — Результат: что получилось, в числах

### Q1: Расскажите о самой сложной технической проблеме, которую вы решали

**Пример ответа (STAR):**

**S:** «В e-commerce проекте с 50K DAU после Black Friday продажи упали на 30%, хотя трафик вернулся в норму.»

**T:** «Мне поручили найти root cause и исправить. Бизнес терял ~$20K/день.»

**A:** «Я проанализировал метрики в Application Insights и нашёл:
1. API latency p95 выросло с 200ms до 3s после Black Friday
2. Причина — таблица OrderHistory выросла с 500K до 5M записей за 3 дня
3. Индекс на Status + CreatedDate отсутствовал
4. EF Core делал full table scan при загрузке "активных заказов"

Исправления:
1. Добавил composite index — латентность упала до 150ms
2. Добавил пагинацию в endpoint
3. Реализовал кэширование горячих данных в Redis
4. Настроил алерт на slow queries > 500ms»

**R:** «Latency вернулось к 150ms за 4 часа. Продажи восстановились на следующий день. После этого я провёл review всех критических запросов и нашёл ещё 3 потенциальные проблемы, которые починили превентивно.»

### Q2: Расскажите о ситуации, когда вы не согласились с решением команды

**Пример ответа (STAR):**

**S:** «Команда решила использовать MongoDB для нового сервиса управления заказами, потому что "все используют NoSQL".»

**T:** «Я считал, что для этого домена реляционная БД подходит лучше, и хотел убедить команду.»

**A:** «Вместо спора я подготовил сравнение:
1. Составил список запросов, которые будет делать сервис — 80% включали JOINы между orders, items, payments
2. Написал прототип одного и того же API на MongoDB и PostgreSQL
3. Показал, что в MongoDB нам нужны embedded documents ИЛИ множественные запросы, а в PostgreSQL — один SQL

Презентовал на техническом review с бенчмарками.»

**R:** «Команда выбрала PostgreSQL. Через полгода добавили 3 новых типа отчётов — все на SQL JOINах, которые в MongoDB потребовали бы сложных aggregation pipelines.»

### Q3: Расскажите о ситуации, когда вам пришлось работать с трудным коллегой

**Пример ответа (STAR):**

**S:** «В команде был Senior-разработчик, который блокировал PR других разработчиков мелкими придирками. Средний цикл PR review вырос до 5 дней.»

**T:** «Как неформальный tech lead, мне нужно было решить проблему, не создавая конфликт.»

**A:** «Я подошёл 1-on-1: "Я заметил, что PR часто возвращаются с большим количеством комментариев. Мне интересно понять твою позицию."

Оказалось, он переживал за качество кода и не доверял junior-разработчикам. Мы договорились:
1. Ввели категории комментариев: blocker / suggestion / nit
2. Только blockers блокируют merge
3. Я взял на себя менторство juniors, чтобы он не чувствовал ответственность за всё
4. Настроили EditorConfig и analyzers для автоматической проверки стиля»

**R:** «Средний цикл PR снизился с 5 дней до 1 дня. Количество production-багов не выросло. Коллега стал фокусироваться на архитектурных замечаниях вместо стилистических.»

### Q4: Расскажите о провале и чему вы научились

**Пример ответа (STAR):**

**S:** «Я предложил и реализовал переход с монолита на микросервисы для проекта с 3 разработчиками и 10K DAU.»

**T:** «Цель была ускорить разработку и упростить деплой.»

**A:** «За 3 месяца мы разбили монолит на 5 сервисов. Добавили RabbitMQ, API Gateway, отдельные базы.»

**R:** «Скорость разработки упала. Вместо одного деплоя — 5 pipelines. Distributed debugging занимал в 3 раза больше времени. Команда из 3 человек не могла поддерживать 5 сервисов.

Через 4 месяца мы частично откатились к Modular Monolith — один деплой, но с чёткими модульными границами.

**Урок:** Микросервисы — это не про технологию, а про организационную структуру. Для маленькой команды монолит с хорошей архитектурой эффективнее. Теперь я всегда начинаю с вопроса "Какой размер команды?" перед тем, как предлагать микросервисы.»

### Q5: Как вы приоритизируете задачи, когда всё "срочно"?

**Пример ответа:**

«Когда всё "срочно" — ничего не срочно. Мой подход:

1. **Определяю impact**: Что блокирует пользователей? Что блокирует коллег? Что может подождать?
2. **Говорю с PO/PM**: "У нас 5 задач, capacity на 3. Какие 3 имеют наибольший бизнес-impact?"
3. **Делаю visible**: Выношу на доску, чтобы все видели загрузку и принимали осознанные решения
4. **Не стесняюсь сказать "нет"**: "Я могу взять эту задачу, но тогда задача X сдвинется на 3 дня. Это ок?"

Конкретный пример: однажды PM, QA и другая команда одновременно пришли с "критическими" задачами. Я собрал 15-минутный sync, мы вместе проранжировали по impact, и оказалось, что "критична" только одна из трёх.»
